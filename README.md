# Project Money

[![Live](https://img.shields.io/badge/live-project--money.online-7c6cff?style=flat&logo=googlechrome&logoColor=white)](https://project-money.online)
[![Stack](https://img.shields.io/badge/stack-React%2018%20·%20Node%2020%20·%20Turso-18e0b5?style=flat)](#stack)
[![License](https://img.shields.io/badge/license-UNLICENSED-lightgrey?style=flat)](#license)

A free personal-finance planner built for India. Plan your salary with the
50/30/20 rule, track daily spending with smart insights, split trips with
friends Splitwise-style, and hit savings goals — in one clean app.

> **Live**: https://project-money.online · **API**: https://project-money-api.onrender.com

![Project Money cover](frontend/public/og.png)

## Features

- **Salary planning** — monthly salary + fixed EMIs → auto 50/30/20 recommended split
- **Daily spending** — one-line expense entry with smart categorization; month-over-month insights
- **Savings goals** — target amount + deadline, progress bar, "if you save ₹X/day you'll make it"
- **Recurring expenses** — rent, subscriptions, SIPs; auto-rolled every month
- **Trips** — budget + members + weighted splits + public share link, Splitwise-style settle-up
- **Admin console** — dedicated `/admin-login`, isolated navigation, user management, feedback, traffic, broadcasts
- **Security** — email OTP sign-up (Resend), bcrypt + JWT (HS256), 3-device cap with FIFO revocation,
  session-level revocation, per-email + per-IP rate limits, strict CORS allowlist, HSTS preload,
  constant-shape responses on all enumeration-sensitive endpoints
- **PWA** — Add-to-Home-Screen on iOS and Android with branded icons
- **Legal** — Privacy, Terms, in-app data export (JSON), self-serve account deletion

## Stack

- **Frontend**: React 18 + Vite 8 + TypeScript, plain CSS with CSS variables, Framer Motion, React Router
- **Backend**: Node 20 + Express 4 (ESM), express-async-errors, express-validator, express-rate-limit, bcrypt, jsonwebtoken
- **Database**: Turso (libSQL / serverless SQLite) — thin async adapter wrapping the sync-style prepared-statement API
- **Email**: Resend (verified sender via `project-money.online` with SPF, DKIM, DMARC)
- **Hosting**: Render (blueprint-managed) · Hostinger (domain) · GitHub Actions (nightly Turso backups)

## Local dev

Requires Node ≥ 20.

```bash
# Terminal 1 — backend
cd backend
cp .env.local.example .env   # fill in TURSO_* and ADMIN_EMAILS
npm install
npm run dev                  # http://localhost:4000

# Terminal 2 — frontend
cd frontend
cp .env.local.example .env.local
npm install
npm run dev                  # http://localhost:5173
```

Without `RESEND_API_KEY` the mailer logs OTP codes to stdout so dev still works
end-to-end — just copy the 6-digit code from the terminal into the UI.

### Create a staging Turso DB (one-time, free)

Keep local experiments far away from prod data:

```bash
turso db create project-money-staging
turso db show project-money-staging --url     # paste into backend/.env
turso db tokens create project-money-staging --expiration none
```

Point `backend/.env` at the staging DB. The schema is created automatically
on first API hit. Prod stays untouched.

## Deploy

The repo ships with `render.yaml` describing two services (API + static web).

1. New → **Blueprint** on Render, point at this repo.
2. On `project-money-api` set:
   - `JWT_SECRET` — long random string (≥ 24 chars)
   - `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN`
   - `RESEND_API_KEY`, `MAIL_FROM="Project Money <no-reply@project-money.online>"`
   - `ADMIN_EMAILS=you@example.com`
   - `CORS_ORIGIN=https://project-money.online,https://project-money-web.onrender.com`
   - `NODE_ENV=production`
3. On `project-money-web` set `VITE_API_BASE=https://project-money-api.onrender.com`.
4. Add a custom domain (optional). Hostinger apex DNS: `ALIAS @ → <web-url>`,
   `CNAME www → <web-url>`.

### Scheduled jobs

**Monthly review email** runs as a secret-gated endpoint on the always-free
API: `POST /api/internal/cron/monthly-review` requires an
`x-cron-secret: <value>` header matching the API's `CRON_SECRET` env var
(auto-generated by Render on first deploy). The real logic lives in
`backend/src/jobs/monthlyReview.js`, imported by both the HTTP route and
`backend/scripts/send-monthly-review.js` (for manual local runs).

Point any external scheduler at it. **cron-job.org** is free, no account
needed:

- URL: `https://project-money-api.onrender.com/api/internal/cron/monthly-review`
- Method: `POST`
- Headers: `x-cron-secret: <value from Render API env>`
- Schedule: 09:00 IST on day 1 of each month

The job is idempotent per `(user_id, month)` via a `monthly_review_log`
table — accidental double-triggers are safe. Pass `?dry=1` to preview
without sending.

**Success reports** use the same secret and scheduler:
`POST /api/internal/cron/clarity-reports` (logic in
`backend/src/jobs/clarityReports.js`). Trigger it daily shortly after
00:00 IST: each run materializes newly completed weekly and 28-day periods,
finishes deferred action metrics, and deletes product events older than 13
months. It is idempotent; `?dry=1` lists work without writing. Admins read the
aggregates at `GET /api/admin/clarity-reports?periodType=&limit=`.

### Operational logs and rollback

Server logs are one JSON object per line from `backend/src/observability/operationalLog.js`.
A line holds a fixed `event` code and only allowlisted fields: request ID, route
pattern (`/api/finance/goals/:id`, never the raw path), method, HTTP status, a
duration bucket, an outcome kind, a stable error code, a record type and numeric
ID, and the account ID on server failures. A field that is not on the allowlist,
or whose value does not match its fixed format, is dropped and only counted in
`droppedFields`. Amounts, names, notes, split JSON, emails, tokens, request or
response bodies, user-agent text, and error messages or stacks are never logged.
Set `OPERATIONAL_LOG_LEVEL` to `debug`, `info` (default), `warn`, `error`, or
`silent` (the default under `NODE_ENV=test`).

Every response carries a server-generated `X-Request-Id`. An unexpected error on
a clarity route, or on any request that sends `X-Clarity-Contract: 1`, returns
`{ error: { code, message, retryable, correlationId } }` where `correlationId` is
that request ID. Other routes keep `{ "error": "Server error" }`. In production
the structured `REQUEST_COMPLETED` event replaces the morgan access log, which
recorded raw URLs, IP addresses, and user agents.

Rollback needs no data change. Set `VITE_FINANCIAL_CLARITY_ENABLED=false` and
rebuild the SPA to return to the legacy UI and read contract, set
`MONTHLY_REVIEW_CALCULATION_MODE=legacy` to send monthly reviews from the legacy
calculation, and leave `CLARITY_SHADOW_COMPARE` off (it logs only mismatch codes
when on). The additive tables and columns stay in place and no record is
deleted or rewritten.

### Backups

Turso provides **automatic point-in-time backups** on every plan,
including the free tier — 24-hour snapshots retained for 30 days. No
cron / dump script needed. To restore, run `turso db restore <db>
--timestamp <ISO>` from the Turso CLI.

## Security notes

- All email-touching endpoints (`register-start`, `register-resend`, `register-finish`,
  `email-change-start`, `password-reset-start`, `trips/:id/invite`) return
  constant-shape responses to avoid account-enumeration oracles.
- JWTs are pinned to HS256 everywhere they're verified. `token_version` acts as a
  per-user kill switch; per-session `sid` revocation lets individual devices be
  signed out.
- Account delete requires the current password and explicitly cleans every
  user-owning table — no reliance on PRAGMA foreign_keys under libSQL.
- IP addresses are never stored raw; only a daily-rotating `sha256(day:salt:ip)[0:24]`
  hash lands in the `visits` table.
- CSV export cells starting with `=`, `+`, `-`, `@`, or TAB are prefixed with `'`
  to defuse Excel/Sheets formula injection.
- CORS refuses to boot in production without a non-wildcard allowlist.
- CSP is `default-src 'none'` on the API; static site serves its own CSP.
- Strict HSTS preload, no `x-powered-by`, body size capped at 64 KB.
